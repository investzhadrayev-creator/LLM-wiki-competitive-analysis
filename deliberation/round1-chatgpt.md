# DELIBERATION ROUND 1 — ChatGPT / аудитор 1

**Дата:** 2026-08-13

## Q1 — Wikilinks и graph view

**Выбор: Вариант 2.**

Соглашаюсь с модификацией архитектора. Моя исходная находка AUD2-024 была направлена не против graph view как пользовательской функции, а против превращения декоративных ссылок в часть контрольного контура. Если `[[wikilinks]]` не участвуют в retrieval, не влияют на eligibility и не проверяются LINT, их ошибочность не способна повредить фактический результат QUERY. Тогда best-effort линкование имеет приемлемую стоимость: владелец сохраняет визуальную навигацию Obsidian, а система не платит за неё ложными orphan-alerts и обязательным обслуживанием графа. Единственное условие: ссылки не должны становиться скрытым источником бизнес-логики позднее без отдельного архитектурного решения. Если появятся типизированные отношения, влияющие на поиск или сравнение, их следует хранить как структурированные данные, а не как свободные wikilinks.

## Q2 — Слой tools/ (validate.py + query.py)

**Выбор: Вариант 1.**

Без `validate.py` большая часть правил v3 остаётся пожеланиями; без `query.py` отбор данных для главной функции системы остаётся недетерминированным. Поэтому вариант 3 закрывает только половину дефекта. Я бы дополнительно потребовал, чтобы оба инструмента были максимально скучными: без LLM внутри, с фиксированным входом/выходом, тестами и fail-closed поведением. `validate.py` должен проверять схему, source_id, допустимые переходы состояний, provenance и запрет использования заблокированных claims. `query.py` должен возвращать воспроизводимый набор claim/card IDs и критерии отбора, чтобы один и тот же запрос к одной версии базы давал тот же candidate set. 200–400 строк Python здесь уменьшают, а не увеличивают архитектурную сложность: они заменяют набор неисполняемых правил одним проверяемым механизмом.

## Q3 — Объём пилота

**Выбор: Вариант 1.**

Полный пилот оправдан, но его результат нельзя трактовать как статистическую гарантию ошибки ≤2% для будущего корпуса. 16 validation-документов нужны прежде всего как adversarial coverage: два вендора, разные классы серверов, сложные таблицы, footnotes, multi-configuration claims и разные методологии maxima. Сокращённый вариант с 50% выборкой снова создаёт слепую зону именно там, где AUD2-016 обнаружил проблему: пропущенные или неверно интерпретированные поля могут не попасть в выборку и не войти в denominator. Сплошная сверка нужна один раз, чтобы измерить одновременно precision и completeness после заморозки схемы. Я бы лишь заранее зафиксировал состав validation set и классы сложности документов, чтобы нельзя было случайно подобрать 16 «удобных» PDF и получить ложное чувство качества.

## Q4 — Page-aware экстрактор

**Выбор: Вариант 1.**

Замена обязательна. Ослабление provenance до «раздел/таблица» не решает основной режим отказа: если парсер разрушил структуру riser matrix, memory population table или footnote, LLM получает неверный вход и может сформировать формально процитированный, но семантически ложный claim. Page-aware extraction одновременно даёт проверяемый anchor и сохраняет локальный контекст. При этом я не считаю выбор конкретного парсера закрытым архитектурным решением: PyMuPDF4LLM/Marker должны пройти тот же Phase A benchmark на реальных Lenovo/HPE PDF. Нужен fallback-протокол: если extraction quality ниже порога или страница image-only/таблично сложная, документ/страница автоматически получает extraction block_reason и не может быть promoted до ручной проверки или альтернативного parser path. Иначе новый экстрактор просто заменит один молчаливый failure mode другим.

## Q5 — Claims: канонический YAML vs отдельная claim-модель

**Выбор: Вариант 1. Согласен с ACCEPT-MOD архитектора.**

Отдельная claim-store + YAML-проекция была защитной реакцией на split-brain v2, но после решения сделать structured claims непосредственно каноническим YAML этот дополнительный слой действительно не нужен для MVP. При ~200 карточках единый источник истины проще мигрировать, инспектировать через Git и валидировать. Однако это работает только при жёстком контракте: тело карточки должно быть производным представлением и не может содержать независимо редактируемые технические значения, которые затем используются QUERY. `validate.py` должен проверять не «похожесть» тела и YAML, а то, что machine-readable claims полностью валидны сами по себе; рендер тела лучше генерировать детерминированно. Если nested YAML станет ограничивать queryability или размеры карточек, тогда переход к отдельной claim-модели будет эволюцией хранения, а не исправлением дефекта целостности.

## Q6 — Оси статусов

**Выбор: Вариант 1, с уточнением. Согласен с ACCEPT-MOD архитектора.**

Мои четыре поля были избыточны. Архитектор правильно применил тот же принцип, что лежит за AUD2-025: состояние, которое можно надёжно вычислить, не следует хранить вручную. `review_status` отражает реальное workflow-событие, а freshness относительно уже загруженных source lineage вычисляется из `sources[]`. `block_reasons[]` достаточно для семантических проблем, которые нельзя вывести чисто из структуры. Уточнение: вычисляемые причины блокировки также не следует постоянно записывать в `block_reasons[]`, иначе двойная бухгалтерия вернётся. Лучше иметь функцию `effective_block_reasons = persisted_semantic_reasons + derived_validation_reasons`; QUERY проверяет именно вычисленную eligibility. Тогда удаление/добавление source автоматически меняет freshness-блокировку без отдельной мутации карточки. Ограничение остаётся честным: система определяет только supersession среди известных/загруженных источников, а не свежесть относительно сайта вендора.

## Q7 — Режим review в рабочем потоке

**Выбор: Вариант 1.**

Риск-ярусный review — лучший компромисс, но eligibility-критичные поля нужно определять не статическим коротким списком `model/SKU/тип памяти`, а по тому, способен ли claim изменить включение модели в shortlist или итог сравнения. Например `cpu_sockets`, поддерживаемый GPU, число PCIe slots, drive topology или power envelope могут быть критичнее SKU памяти для конкретного QUERY. После пилота следует классифицировать поля/claim types по impact-tier и установить sampling rate по наблюдаемой ошибке каждого класса. При любой ошибке в выборке эскалация должна распространяться не только на текущую карточку, но и на соответствующий pipeline/document-layout cohort, иначе систематическая ошибка парсинга таблиц останется в соседних карточках. Вариант 2 операционно неустойчив, вариант 3 не ловит семантически правдоподобные ошибки.

## Q8 — OUTPUT-LINT

**Выбор: Вариант 2. Возражаю против DEFER.**

После того как архитектор уже принял структурированные `inputs + formula` для derived values, отсутствие автоматического пересчёта становится искусственной дырой. Конкретный failure mode: два исходных claim корректны и имеют provenance, но LLM ошибается в процентной разнице, сумме, нормализации или конверсии; человек видит правдоподобное число и пропускает ошибку. Ни validation wiki, ни provenance это не обнаружат. Стоимость закрытия мала только если формулы не свободный текст: MVP должен разрешать ограниченный DSL/whitelist операций (`+ - * /`, ratio, percent_delta, unit conversion с фиксированной таблицей). `validate.py` пересчитывает результат и блокирует сохранение отчёта при расхождении. Это не отдельный сложный OUTPUT-LINT-продукт, а естественное расширение уже существующего deterministic validator. Поэтому defer экономит мало, оставляя известный механизм ложного аналитического вывода.

**Критичная цена ошибочного решения: Q4.** Если extraction layer систематически разрушает таблицы или контекст, система начинает производить неверные первичные claims с убедительным provenance; последующие validator, review и QUERY работают уже на испорченной фактической базе и не способны надёжно восстановить утраченную семантику.
