## 0. Changelog v1.0 → v2.0

Все изменения — результат внутреннего аудита от 2026-08-12 (12 находок) и сканирования существующих open-source реализаций паттерна «LLM Wiki». Полная диспозиция находок — в Приложении A. Ключевые изменения:

1. **Git добавлен в стек как обязательный фундамент** (не опция): неизменяемая история, диффы каждой операции, откат.
2. **LINT переведён в read-only режим**: производит отчёт, правки вносятся только после валидации человеком.
3. **Введено обязательное поле provenance** для каждого извлечённого значения.
4. **Введён протокол разрешения противоречий** через `contradictions.md` — истину решает человек, не LLM.
5. **Введены lifecycle-статусы страниц** (draft / active / stale / quarantine).
6. **qmd исключён из базового стека** (отложен до фактической необходимости); `index.md` удалён (заменён Dataview).
7. **log.md заменён на git log** с дисциплиной commit-сообщений.
8. **Введён контракт хранения технических значений** (дословно как в источнике) и версионирование схемы.
9. **Введён обязательный пилот с предрегистрированными порогами качества** перед промышленной загрузкой.
10. **Права доступа получили технический enforcement** (файловая система + git), а не только текст в промпте.

## 1. Концепция и разделение ролей

Система: персональная база знаний для каталогизации и конкурентного анализа серверного оборудования (Lenovo vs HP и др.). Методология: паттерн «LLM Wiki» (Andrej Karpathy) — инкрементальное построение персистентной базы плоских Markdown-файлов вместо RAG-пересборки контекста на каждый запрос.

**Матрица ответственности:**

| Роль | Отвечает за |
|---|---|
| Человек-оператор | Курирование и загрузка первоисточников; формулирование бизнес-задач (ТЗ, запросы на сравнение); **валидация отчётов LINT**; **разрешение противоречий между источниками**; выборочная проверка диффов INGEST |
| LLM-агент | Чтение, перевод, извлечение характеристик, разметка; обновление файлов wiki/; перекрёстные ссылки; git-коммиты с атрибуцией; формирование отчётов |

**Принцип (v2):** LLM никогда не является финальным судьёй истинности данных. Любое противоречие между источниками, любое исправление существующей карточки, любой результат LINT проходит через человека.

## 2. Технологический стек

| Компонент | Инструмент | Статус |
|---|---|---|
| Хранилище и интерфейс | Obsidian (локальные Markdown-файлы) | Базовый |
| Версионирование и enforcement | **Git** (весь vault — git-репозиторий с первого коммита) | **Базовый, обязательный** |
| Вычислительный узел (агент) | Claude Code (доступ на чтение/запись в ФС) | Базовый |
| Аналитика и сводные таблицы | Плагин Dataview (запросы к YAML frontmatter) | Базовый |
| Динамический индекс каталога | Dataview-запрос (заменяет ручной index.md) | Базовый |
| Текстовый поиск | grep / встроенный поиск Obsidian | Базовый |
| Гибридный поиск (qmd или аналог) | — | **Отложен.** Вводится только когда grep + Dataview фактически перестанут справляться. Критерий пересмотра: >200 карточек И систематические промахи поиска релевантных карточек в QUERY |
| Конвертация PDF → Markdown | markitdown (Microsoft) при операции INGEST | Базовый |

**Обоснование отказа от qmd в базовом стеке:** каталог из 100–200 карточек с плотным YAML — это структурированные данные, где точный матчинг по полям Dataview превосходит векторный поиск (семантический поиск по «2U, 32 DIMM slots» заведомо хуже фильтра по полю `form_factor`). Векторный индекс также создаёт проблему переиндексации (устаревший индекс находит устаревшие версии карточек), которую в базовом стеке решать не нужно.

## 3. Архитектура данных

### 3.1. Слои и enforcement прав доступа

| Слой | Содержимое | Права | Механизм enforcement |
|---|---|---|---|
| `raw/` | Оригинальные даташиты, мануалы, спецификации (EN), брифы ТЗ | Только чтение для агента | (1) Инструкция в CLAUDE.md; (2) **файловые атрибуты read-only на уровне ОС**; (3) git — любое изменение видно в диффе и откатывается |
| `wiki/` | Карточки оборудования (RU), `contradictions.md` | Запись агентом; **правки человека допустимы** через git (агент видит дифф и обновляет связи) или через поле `human_notes` | Git-диффы каждой операции |
| `outputs/` | Аналитические отчёты, таблицы сравнения, подборки под ТЗ, **отчёты LINT** | Запись агентом, валидация человеком | Git |
| `audits/` | Файлы аудитов и диспозиции (процесс развития самой системы) | Запись человеком | Git |

**Изменение против v1:** запрет человеку редактировать `wiki/` снят. Оператор — доменный эксперт; его правки — самый дешёвый канал коррекции. Консистентность обеспечивается git-диффом, а не запретом.

### 3.2. Что удалено из v1

- **`wiki/index.md`** — ручной каталог, обречённый на рассинхронизацию («двойная бухгалтерия»). Заменён динамическим Dataview-запросом по YAML-полям: всегда актуален, нулевая стоимость поддержки.
- **`wiki/log.md`** — append-only «по договорённости», ведётся тем же агентом, который его может переписать. Заменён `git log`: каждая операция агента = один коммит с сообщением фиксированного формата `[INGEST|QUERY|LINT|MIGRATE] <объект>: <краткое описание>`. Криптографическая гарантия неизменяемости истории.

### 3.3. Версионирование источников

Даташиты вендоров регулярно ревизуются. Правила:

- Имя файла в `raw/` включает ревизию/дату документа, если она есть в источнике: `lenovo-sr650-v3_datasheet_2026-03_rev1.4.pdf`.
- Карточка в `wiki/` несёт поля `source_doc` и `source_doc_date` (см. схему).
- Новая ревизия даташита = **явная** операция обновления карточки отдельным коммитом с указанием обеих ревизий в сообщении. Молчаливое смешивание данных двух ревизий запрещено.

## 4. Схема данных (YAML Frontmatter)

### 4.1. Обязательные служебные поля каждой карточки

```yaml
schema_version: "2.0"          # версия схемы; изменение схемы = операция MIGRATE
status: draft                  # draft | active | stale | quarantine
source_doc: "raw/lenovo-sr650-v3_datasheet_2026-03_rev1.4.pdf"
source_doc_date: "2026-03"
source_revision: "1.4"
ingested: "2026-08-13"
last_verified: "2026-08-13"
human_notes: ""                # свободное поле для правок/комментариев оператора
```

### 4.2. Lifecycle-статусы (заимствовано из MeMex-Zero-RAG)

| Статус | Значение |
|---|---|
| `draft` | Карточка создана INGEST, дифф ещё не просмотрен человеком (выборочно) |
| `active` | Рабочая карточка |
| `stale` | Источник устарел (вышла новая ревизия даташита, карточка не обновлена) |
| `quarantine` | LINT нашёл противоречие или unsourced-значения; карточка исключается из сравнительных отчётов до разрешения человеком |

**Правило QUERY:** карточки в статусе `quarantine` не участвуют в сравнительных таблицах и подборах под ТЗ. Если релевантная карточка в карантине — отчёт явно это указывает.

### 4.3. Контракт технических значений (критично для сравнимости)

1. **Числовые значения и техническая номенклатура хранятся ДОСЛОВНО как в источнике**: единицы, суффиксы, обозначения вендора (`DDR5-4800 RDIMM`, `2U`, `TDP 350W (configurable)`). Переводится только проза (описания, примечания).
2. **Единицы измерения — часть контракта схемы**: для каждого сравниваемого поля схема фиксирует каноническую единицу (GB vs GiB, MT/s vs MHz, TDP default vs configurable). Если источник даёт значение в другой единице — хранится дословное значение источника + нормализованное поле с явной пометкой конверсии.
3. **Provenance на уровне значения**: каждое извлечённое техническое значение в теле карточки сопровождается ссылкой на источник в формате `[src: <файл>, стр. N / раздел X]`. Значение без provenance = ошибка LINT (🔴 ERROR, не warning). *(Протокол заимствован из MeMex-Zero-RAG «Zero Hallucination Protocol».)*

### 4.4. Доменные поля (набросок, финализируется на пилоте)

`vendor, model, generation, form_factor, cpu_sockets, cpu_supported, ram_slots, ram_max, ram_type, drive_bays, storage_controllers, network_onboard, pcie_slots, psu_options, management, warranty` — точный состав и канонические единицы фиксируются по итогам пилота (раздел 7), не до него.

### 4.5. Версионирование схемы

Изменение состава или имён полей = новая `schema_version` + операция MIGRATE (раздел 5.4), которая обновляет ВСЕ карточки одним коммитом. Запрещено сосуществование карточек с разными версиями схемы в статусе `active` — иначе Dataview-таблицы молча теряют половину строк.

## 5. Рабочие процессы (Workflows)

Фактический триггер всех операций — **человек запускает сессию агента** (Claude Code — сессионный инструмент, не демон; никакого file watcher в системе нет и не заявляется).

### 5.1. INGEST — загрузка и парсинг

1. Оператор кладёт даташит в `raw/` (имя файла — по правилам 3.3) и даёт команду.
2. Агент конвертирует PDF → Markdown (markitdown), полностью читает документ.
3. Извлекает характеристики по схеме, создаёт/обновляет карточку в `wiki/` со статусом `draft`, каждое значение — с provenance.
4. Связывает карточку вики-ссылками `[[ ]]` с релевантными существующими.
5. **Если извлечённое значение противоречит уже существующему в базе** (например, другая ревизия даташита или пересечение с карточкой конкурента) — агент НЕ выбирает «правильное»: фиксирует оба значения в `wiki/contradictions.md` с источниками и останавливается с вопросом к оператору.
6. Коммит: `[INGEST] lenovo-sr650-v3: created from datasheet rev1.4 (2026-03)`.
7. Оператор выборочно смотрит дифф (обязательно — на пилоте; выборочно — в рабочем режиме) и переводит карточку в `active`.

### 5.2. QUERY — запрос, сравнение, подбор под ТЗ

1. Триггер: запрос оператора («Сравни новый сервер HP из raw/ с аналогами Lenovo»).
2. Отбор релевантных карточек: **Dataview-фильтр по полям схемы** (форм-фактор, поколение, класс) + grep по тексту. Только `active` карточки.
3. Агент читает отобранные карточки, синтезирует отчёт. Каждое число в отчёте наследует provenance из карточки.
4. Отчёт (RU) сохраняется в `outputs/`, коммит `[QUERY] ...`. Валидация человеком.

### 5.3. LINT — аудит качества базы (READ-ONLY)

1. Триггер: команда оператора (рекомендуемый ритм — ежемесячно или после каждых ~20 INGEST).
2. Агент рекурсивно проверяет `wiki/`: логические противоречия в спецификациях; значения без provenance; «сиротские» страницы; карточки со `schema_version` ≠ текущей; карточки, чей `source_doc_date` старше известной ревизии в `raw/`.
3. **Агент НЕ вносит ни одного исправления.** Результат — отчёт в `outputs/lint-YYYY-MM-DD.md` со списком находок и предлагаемых исправлений.
4. Оператор проходит отчёт и утверждает исправления (все / выборочно). Только после этого агент вносит утверждённые правки отдельным коммитом `[LINT-FIX] ...` со ссылкой на отчёт.

**Обоснование:** LLM, самостоятельно «исправляющий» найденные им же противоречия с полными правами записи, — это не контроль качества, а второй проход генерации поверх первого, с риском затереть верную версию. Единственный внешний судья в системе — человек.

### 5.4. MIGRATE — эволюция схемы (новая операция)

1. Триггер: утверждённое оператором изменение схемы (новое поле, переименование, изменение канонической единицы).
2. Агент обновляет описание схемы в CLAUDE.md, затем все карточки `wiki/` до новой `schema_version` одним коммитом `[MIGRATE] schema 2.0 -> 2.1: added <field>`.
3. LINT-проверка сразу после миграции: ни одной `active` карточки со старой версией.

## 6. Управление системой (CLAUDE.md)

Конфигурационный документ в корне репозитория. Фиксирует: архитектуру и права доступа к папкам; полную YAML-схему с каноническими единицами; контракт технических значений (4.3); формат provenance; правила нейминга файлов и стандарты перевода терминов; протоколы всех четырёх операций; формат commit-сообщений; протокол противоречий.

**Принцип:** CLAUDE.md — инструкция для агента, но НЕ механизм безопасности. Всё, что критично (неизменяемость raw/, история операций), продублировано техническим enforcement (ОС + git). Скелет CLAUDE.md собирается из двух доноров: структура и workflow-команды — из SamurAIGPT/llm-wiki-agent; citation-протокол, contradictions и lifecycle — из MeMex-Zero-RAG SCHEMA.md (оба MIT).

## 7. Пилот перед промышленной загрузкой (обязательный гейт)

Система не масштабируется до 100+ карточек с неизмеренной ошибкой экстракции.

**Протокол пилота:**
1. Объём: **10 даташитов Lenovo** разных классов (rack 1U/2U, tower, edge).
2. Оператор вручную сверяет **каждое** извлечённое поле каждой карточки с оригиналом.
3. **Предрегистрированные пороги (фиксируются ДО пилота, не подгоняются под результат):**
   - Ошибки в числовых полях: ≤ 2% от общего числа извлечённых значений;
   - Ошибки в модельных номерах и номенклатуре (model, CPU SKU, тип памяти): **0**;
   - Значения без provenance: **0**;
   - Ошибки перевода, искажающие технический смысл: 0.
4. Порог не пройден → разбор класса ошибок, правка CLAUDE.md/схемы, повторный пилот на 10 НОВЫХ даташитах. Порог пройден → промышленная загрузка + финализация доменных полей схемы (4.4).

## 9. Открытые вопросы для внешних аудиторов

Аудиторам (ChatGPT, Grok) предлагается в том числе, но не ограничиваясь:

1. Достаточен ли протокол пилота (7)? Корректны ли пороги?
2. Есть ли дыры в контракте технических значений (4.3), которые сломают сравнимость Lenovo vs HP (разные методологии измерения у вендоров: max RAM «per socket» vs «total», условные конфигурации)?
3. Выдержит ли схема provenance «стр. N» тот факт, что markitdown-конвертация теряет пагинацию PDF?
4. Не пропущен ли какой-либо сценарий рассинхронизации wiki/ и raw/ при правках человека?
5. Масштабируемость: на каком реальном объёме Dataview + grep деградируют и по какому сигналу вводить гибридный поиск?
6. Что ещё избыточно и можно удалить?
