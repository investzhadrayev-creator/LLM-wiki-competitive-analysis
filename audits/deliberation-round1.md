## Вопрос Q1 — Wikilinks и graph view (исходно: AUD2-024)

Автолинкование `[[ ]]` и orphan-check: для retrieval не используются (отбор идёт по YAML-полям), создают постоянную LLM-стоимость и ложные LINT-сигналы; но graph view — часть ценности Obsidian для владельца.

- **Вариант 1:** удалить автолинкование и orphan-check полностью (позиция ChatGPT в AUD2-024).
- **Вариант 2:** линкование остаётся best-effort: агент ставит ссылки при INGEST, но LINT их не проверяет, orphan — не находка, стоимость ошибки ноль.
- **Вариант 3:** оставить как в v2 (обязательное линкование + orphan-check).

**Позиция Claude: Вариант 2.** Ценность graph view субъективна и принадлежит владельцу — не архитектору её отменять. Но платить за неё контрольным контуром (LINT-проверки, ложные сигналы) нельзя: контур должен охранять данные, не эстетику. Best-effort даёт граф бесплатно по рискам: ошибка в ссылке ничего не ломает, потому что ссылка ни на что не влияет.

## Вопрос Q2 — Слой tools/ (Python: validate.py + query.py)

Оба аудита независимо пришли к выводу: без исполняемого validator система сгниёт (AUD2-010 формально, A1/A2/A11 операционно). Но это философское изменение: проект перестаёт быть «только Markdown + агент».

- **Вариант 1:** принять — детерминированные проверки и отбор карточек выполняет код (~200–400 строк Python, пишется один раз).
- **Вариант 2:** отклонить — все проверки остаются на LLM и человеке.
- **Вариант 3:** промежуточный — только validate.py (гейт качества), QUERY-отбор остаётся на LLM+grep.

**Позиция Claude: Вариант 1.** Это единственный пункт, где оба аудитора сошлись в диагнозе с разных сторон, — самый сильный сигнал всего аудита. Вариант 3 хуже, чем кажется: без query.py остаётся дефект AUD2-005 (Dataview недоступен агенту headless) и недетерминированный отбор карточек — то есть QUERY-результаты невоспроизводимы, что для системы сравнения оборудования обесценивает главный продукт.

## Вопрос Q3 — Объём пилота

- **Вариант 1:** полный — Фаза A (schema discovery, 5 док.) + Фаза B (blind validation: 10 Lenovo + 6 HP/HPE, сплошная ручная сверка всех полей). ~2–3 вечера работы владельца.
- **Вариант 2:** сокращённый — Фаза B: 8 Lenovo + 4 HP; сплошная сверка только eligibility-критичных полей, остальные — 50% выборка.

**Позиция Claude: Вариант 1.** Пилот — единственная точка, где истинная ошибка системы измерима сплошной сверкой; после него все оценки качества — экстраполяция с пилота. Сэкономленный вечер сейчас = неизвестная ошибка навсегда. Контраргумент Grok (перегруз оператора, A1) валиден для рабочего режима, но пилот — разовое событие, а не поток.

## Вопрос Q4 — Замена markitdown на page-aware экстрактор (PyMuPDF4LLM / Marker)

Кластер C2: markitdown теряет пагинацию (ломает provenance «стр. N») и разрушает сложные таблицы вендоров.

- **Вариант 1:** заменить — PyMuPDF4LLM базово, Marker для тяжёлых таблиц; markitdown допустим только как вторичное «читабельное» представление.
- **Вариант 2:** оставить markitdown, ослабить формат provenance до «раздел/таблица» без страниц.

**Позиция Claude: Вариант 1.** Вариант 2 лечит симптом (формат ссылки), но не болезнь (разрушенные таблицы = неполные значения = LLM додумывает). Grok A5 показал, что доминирующий класс контента серверных даташитов — именно matrix-таблицы конфигураций. Экстрактор — фундамент качества всего конвейера.

## Вопрос Q5 — Реализация claims: канонический YAML vs полная claim-модель (мой ACCEPT-MOD на AUD2-001; право возражения — ChatGPT)

ChatGPT предложил: claim = отдельная каноническая сущность `{raw, normalized, unit, source_id, scope}`, YAML — детерминированная проекция. Claude упростил: канон — сам YAML frontmatter (claims как структуры внутри него), тело карточки — рендер; validate.py запрещает расхождение.

- **Вариант 1:** упрощение Claude (YAML канон).
- **Вариант 2:** полная модель ChatGPT (отдельное хранение claims + генерация YAML-проекции).

**Позиция Claude: Вариант 1.** Обе модели закрывают split-brain. Разница — количество движущихся частей: Вариант 2 добавляет слой генерации проекций, то есть ещё один процесс, который может рассинхронизироваться и требует собственной валидации. Для одного оператора и ~200 карточек единый источник в YAML проще и достаточен; миграция к Варианту 2 возможна позже без потери данных.

## Вопрос Q6 — Оси статусов: 2 поля vs 4 (мой ACCEPT-MOD на AUD2-006; право возражения — ChatGPT)

ChatGPT предложил: `review_status` + `freshness_status` + `quality_status` + `block_reasons[]`. Claude упростил: `review_status` (draft/active) + `block_reasons[]`; freshness вычисляется validate.py из sources[] против raw/, не хранится.

- **Вариант 1:** упрощение Claude (2 поля, freshness вычисляемый).

## Вопрос Q7 — Режим review в рабочем потоке (мой ACCEPT-MOD на A1; право возражения — Grok)

Grok показал: 6–8 ручных действий на INGEST убьют дисциплину к 30-й карточке. Claude предложил риск-ярусный review: eligibility-поля (model, SKU, тип памяти) — проверка всегда; остальные — выборка 1 из N (N калибруется по ошибке пилота) с эскалацией до сплошной при найденной ошибке.

- **Вариант 1:** риск-ярусный review (Claude).
- **Вариант 2:** жёстче — сплошная проверка всех полей каждой карточки всегда (безопаснее, но подтверждает прогноз A1 о перегрузе).
- **Вариант 3:** мягче — только автоматика validate.py, человек смотрит лишь contradictions.

**Позиция Claude: Вариант 1.** Вариант 2 математически безопаснее, но операционно нереален — сам Grok это доказал; правило, которое не будут выполнять, опаснее более слабого правила, которое будут. Вариант 3 оставляет семантические ошибки экстракции (не ловимые схемой) без единого человеческого взгляда. Ярусность ставит человеческое внимание туда, где цена ошибки максимальна.

## Вопрос Q8 — OUTPUT-LINT: defer или в MVP (мой DEFER на часть AUD2-022; право возражения — ChatGPT)

ChatGPT: derived-значения в отчётах (проценты, GB/U, агрегаты) не покрыты никакой проверкой. Claude принял хранение inputs+формулы для derived-значений, но отложил отдельный OUTPUT-LINT за MVP (отчёты валидирует человек по определению слоя outputs/).

- **Вариант 1:** defer (Claude) — inputs+формула фиксируются, автоматической проверки outputs в MVP нет.
- **Вариант 2:** в MVP — validate.py пересчитывает формулы derived-значений в отчётах.

**Позиция Claude: Вариант 1, слабо держимая.** Признаю: раз formula+inputs уже структурированы (это принято), их пересчёт — ~20 строк кода, и Вариант 2 дёшев. Держу defer только ради минимизации скоупа MVP. Если оба аудитора выберут Вариант 2 — соглашусь без спора.
